Worktree development environments
=================================

``alliance-platform-dev`` gives every Git worktree its own runnable development environment.
It is aimed at Alliance Django projects where an environment is more than one process: Django,
Vite, PostgreSQL, background workers, and optional Portless routing all need to agree about which
checkout they belong to.

Projects expose the tool through a checked-in ``bin/dev`` launcher. Humans and coding agents use
that project command, while the launcher obtains the pinned ``alliance-platform-dev`` release
from PyPI with ``uvx``.

Why a worktree needs more than another checkout
-----------------------------------------------

A Git worktree separates files, but it does not automatically separate runtime state. Consider a
normal feature-worktree setup:

.. code-block:: bash

   git worktree add ../my-project-billing -b feature/billing
   cd ../my-project-billing

Without a worktree-aware runner, starting the project here normally reuses the same defaults as
the original checkout:

* Django tries the usual port, such as 8000;
* Vite tries its usual port;
* both checkouts point at the same development database;
* worker processes have no durable identity tying them to one checkout; and
* a Git-ignored ``.env`` is not present in the new worktree, so any required values must be
  copied, linked, exported by the shell, or configured again.

That is manageable for one checkout, but fragile when two features—or two coding agents—need to
run at once. Port collisions are the obvious failure. Sharing a database is worse: migrations,
fixtures, and edits made for one branch can silently affect the other.

With ``bin/dev``, the same setup becomes:

.. code-block:: bash

   git worktree add ../my-project-billing -b feature/billing
   cd ../my-project-billing

   bin/dev up
   bin/dev url

The runner derives a stable identity from the canonical worktree path, creates or reuses a
database for that identity, allocates non-conflicting ports, and starts Django, Vite, and every
configured service in an isolated tmux session.

The runner deliberately does not copy application secrets. Values generated by the development
environment—database name, ports, worktree identity, and host—are supplied automatically. Values
owned by the application can still come from a worktree ``.env``, the invoking shell, or a private
user-level configuration layer. This keeps secret handling explicit while removing the repetitive
runtime wiring that is safe to derive.

What it brings
--------------

Each worktree receives:

* a stable project/worktree identity that does not change when its branch is renamed;
* a PostgreSQL database name unique to that project and worktree;
* independently allocated Django and Vite ports;
* a dedicated tmux session containing Django, Vite, and configured extra processes;
* generated environment values shared consistently by servers, management commands, tests, and
  foreground commands;
* readiness checks, bounded logs, restart and cleanup commands; and
* machine-readable status and URL output for scripts and agents.

The database is retained across ``down`` and ``up`` by default. Processes can therefore be stopped
without throwing away useful state, while ``down --drop-db`` provides an explicit clean reset.

Adding it to an existing project
--------------------------------

Run the installer from the root of an existing Django project:

.. code-block:: bash

   uvx --from alliance-platform-dev alliance-dev install

It discovers ``manage.py`` and asks you to confirm ambiguous Django layouts. Vite is assumed to
use the repository-root ``package.json``, as it does in the standard project layout. The command
creates a checked-in ``bin/dev`` launcher and ``config/dev.toml``.

The installer does not edit Django settings. At the end it prints a block to copy into the
project's development settings module, normally ``dev.py``. The block trusts Portless localhost
origins for CSRF, preserves the browser hostname through the proxy, and tells Django that the
original request used HTTPS. Keep these proxy-trust settings development-only.

For agents or bootstrap scripts, ``--yes`` accepts unambiguous discoveries without prompting:

.. code-block:: bash

   uvx --from alliance-platform-dev alliance-dev install --yes

Existing ``bin/dev`` and ``config/dev.toml`` files are never replaced non-interactively unless
``--force`` is also supplied. Review the printed Django settings and generated command
arrays—especially the test, lint, and check scripts—before running ``bin/dev doctor`` and
``bin/dev up``.

When Husky pre-commit or pre-push hooks are present, the installer also offers to create a small
hook wrapper and update those hooks. It uses the managed worktree environment after ``bin/dev up``
and preserves the inherited hook environment before a worktree has managed state. This prevents a
hook in one worktree from accidentally testing against another worktree's database.

Several environments at the same time
--------------------------------------

Two terminals can run two complete environments concurrently:

.. code-block:: bash

   # Terminal 1
   cd ../my-project-billing
   bin/dev up
   bin/dev url

   # Terminal 2
   cd ../my-project-reporting
   bin/dev up
   bin/dev url

Both can have Django, Vite, workers, and other required services running. Their database names,
tmux sessions, and ports are distinct.

With a compatible Portless installation, each worktree also receives a memorable, unique browser
hostname. This is especially useful for cookies, redirects, callbacks, tenant subdomains, and
sharing URLs between a browser and an agent. Without Portless, the environments remain isolated
and browser-accessible through different localhost ports, for example
``http://localhost:8000`` and ``http://localhost:8001``.

Use ``bin/dev status --all`` to see the active worktrees for a project and ``bin/dev url`` to get
the current worktree's browser URL.

Human development workflow
--------------------------

A typical interactive loop is:

.. code-block:: bash

   bin/dev up
   bin/dev status
   bin/dev logs django

   bin/dev manage shell
   bin/dev test app.tests.test_billing
   bin/dev jstest src/billing
   bin/dev lint

   bin/dev restart django
   bin/dev down

``up`` is idempotent when the environment is already healthy. ``manage``, ``test``, ``jstest``,
``lint``, and ``run`` receive the same generated worktree environment, so one-off commands cannot
accidentally fall back to the original checkout's database.

Use ``bin/dev attach`` when direct tmux access is useful, and ``bin/dev doctor`` when diagnosing
local tool, PostgreSQL, tmux, or Portless setup.

Agent-owned worktrees
---------------------

Coding agents benefit from the same contract. Give each agent its own worktree and let it own the
environment for the duration of its task:

.. code-block:: bash

   git worktree add ../agent-billing -b codex/agent-billing
   cd ../agent-billing

   bin/dev up
   bin/dev status --json
   bin/dev url --json

   # Implement and verify against this worktree's database and services.
   bin/dev test app.tests.test_billing
   bin/dev check

   bin/dev down

Agents can parse the JSON forms instead of scraping terminal output. Multiple agents can run
their stacks simultaneously without coordinating port numbers or sharing a mutable database. A
failing agent environment can be inspected with ``logs`` before it is stopped; cleanup remains
scoped to that worktree. Non-interactive database deletion requires the explicit
``bin/dev down --drop-db --yes`` form.

The runner keeps a private machine-wide registry of databases and sessions associated with each
worktree. Stopping an agent with plain ``down`` retains both its database and registry record for
later reuse; use ``down --drop-db --yes`` before removing a disposable agent worktree when its
database is no longer needed. The registry is stored below ``$XDG_STATE_HOME/alliance/dev`` (or
``~/.local/state/alliance/dev``) so resource ownership is not lost merely because an agent deletes
the worktree directory.

From any remaining worktree for the same project, inspect and remove retained agent environments:

.. code-block:: bash

   bin/dev env list
   bin/dev env remove agent-billing-0123456789 --yes

Removal stops a live matching session and drops its database only when the registry says the
runner created it. A pre-existing or otherwise unowned database is left untouched.

Starting quickly from a template database
-----------------------------------------

Creating a realistic development database can dominate worktree startup time. A project may need
large fixtures, reference datasets, search indexes, or expensive ``createdevdata`` processing that
is identical for every worktree.

Set ``database_template`` to a prepared local PostgreSQL database to use that database as a fast
baseline:

.. code-block:: toml

   database_template = "my_project_dev_template"

This is often a machine-specific setting, so it fits naturally in the private user/project layer
opened by:

.. code-block:: bash

   bin/dev config edit global

When a worktree database does not yet exist, ``bin/dev up`` verifies the template, clones it with
PostgreSQL, runs current migrations, and skips ``createdevdata``. Subsequent starts reuse the
worktree database normally. The team remains responsible for refreshing the template when its
baseline data becomes stale, but each new worktree gets a near-instant independent copy instead of
rebuilding the same data.

Adapting cloned data with ``db_prepare_command``
-------------------------------------------------

A cloned or freshly seeded database sometimes contains values that must differ per worktree.
``db_prepare_command`` names a Django management command, expressed as management-command argv,
that runs once after a new worktree database has been created, migrated, and—when no template is
used—seeded:

.. code-block:: toml

   db_prepare_command = ["prepare_worktree_db"]

The command receives the generated database environment. When Portless is selected it also
receives ``DEV_BASE_HOST``, containing the worktree's bare hostname.

For example, a multi-tenant application may store one ``http_host`` per organisation. Its normal
seed data might use canonical hosts such as ``council-a.my-project.localhost``. A small,
project-owned ``prepare_worktree_db`` command can preserve the organisation prefix while replacing
the canonical suffix with the current ``DEV_BASE_HOST``. The result is that every organisation in
every worktree remains reachable through a unique Portless subdomain, without manually editing
records after cloning the database.

That preparation command should be intentionally narrow:

* read and validate ``DEV_BASE_HOST`` as a bare hostname;
* update only records using the expected canonical suffix;
* preserve tenant or organisation prefixes;
* be idempotent and safe to re-run;
* do nothing, or use a documented fallback, when Portless is not active; and
* fail with an actionable message when existing data is not in the expected shape.

Because preparation runs only when the worktree database is created, normal ``down``/``up`` cycles
do not rewrite application data. If the hostname policy changes later, the same command can be run
explicitly with ``bin/dev manage prepare_worktree_db``.

Configuring the complete stack
------------------------------

Django and Vite are built in. Project-specific long-running services are committed as argument
arrays so every human and agent starts the same required stack:

.. code-block:: toml

   [[extra_processes]]
   name = "worker"
   command = ["uv", "run", "python", "manage.py", "run_worker"]
   cwd = "django-root"
   required = true

Required processes participate in readiness and failure reporting. Optional supporting processes
can set ``required = false``. Commands are passed as argv rather than interpolated into shell
source.
